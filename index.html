01 / 안전망

회귀 방지 장치를 스스로 깝니다

테스트가 0개고 CI가 프론트를 검사하지 않던 프로젝트에 Vitest와 검사 워크플로를 직접 만들어 넣었습니다. 커밋 메시지에 이렇게 적었습니다 — “테스트를 아무도 강제하지 않던 것”.

02 / 접근성

요구받기 전에 잡습니다

포커스 트랩, 키보드 내비게이션, prefers-reduced-motion, 레이아웃 시프트. “보기 좋게”가 아니라 키보드·스크린리더·모션 민감 사용자·터치 기준으로 훑습니다.

03 / 계약

백엔드를 기다리지 않습니다

MSW 목으로 계약을 먼저 세워 화면을 완성합니다. 2인 팀에서 대기 시간을 0으로 만드는 방법이고, 실제로 두 프로젝트에서 그렇게 했습니다.

개인 · 개발 1인

PROOVIT

AI 빌드 시즌제 리그 플랫폼. 3인 팀의 개발 전담 1인으로 프론트·백엔드·DB·배포·인프라를 전부 맡았습니다. 현재 배포 운영 중.

Next.js 16 · TypeScript · Prisma · PostgreSQL(Neon) · Auth.js · Zod · Upstash · Vercel
64커밋 / 11일
23,800직접 작성 라인
34페이지 라우트
43DB 모델
문제

시즌제라 화면마다 “지금 시즌 단계가 뭔지, 이 팀이 어느 스테이지인지”에 따라 접근 여부가 갈립니다. 화면마다 if (phase === 'recruiting') 식으로 쓰기 시작하면 규칙이 바뀔 때 34곳을 전부 고쳐야 합니다.

판단

판정을 canAccess() 한 곳으로 모으고, phase 값을 직접 비교하지 않도록 술어 한 겹을 끼웠습니다. 그리고 판정 로직 파일에서 ORM 의존을 걷어냈습니다 — 판정이 순수해야 클라이언트 번들이 깨지지 않기 때문입니다.

결과

이후 실제로 시즌 단계 값이 10개에서 6개로 통합되는 변경이 왔습니다. 고친 파일은 4개였고 라우트 34개와 판정표는 한 줄도 건드리지 않았습니다. 검증 케이스 52개 통과.

“혹시 몰라서” 넣은 추상화가 아닙니다. 기획이 확정 전이라는 걸 알고 변할 축을 미리 격리한 것이고, 실제로 그 축이 변했습니다.
또 하나

자동 생성된 마이그레이션이 운영 데이터를 지울 뻔했습니다. Prisma가 컬럼을 DROP + ADD로 처리하고 있어서, 그대로 돌리면 시즌 이름이 사라지고 기존 구글 계정 연결이 끊깁니다.

자동 생성본을 버리고 5곳을 직접 작성했습니다 — RENAME COLUMN, USING 캐스트, 옛 값 5종을 새 값으로 접는 CASE 매핑. 빈 DB부터 마이그레이션 5개를 재생해 테이블 43개·ENUM 33개 생성을 확인했고, 운영 데이터 손실은 0이었습니다.

그리고

운영자가 로그 없이 데이터를 바꿀 수 있는 구조였습니다. 감사 로그 함수가 트랜잭션을 인자로 받도록 설계해(writeAudit(tx, …)) 로그 없는 운영 변경을 애초에 작성할 수 없게 만들었습니다. 사유는 NOT NULL, 5자 미만은 거절.

재직 · 프론트 단독

누띠 사진 놀이터

강아지 사진을 AI로 변환해 쇼핑몰 유입으로 잇는 서비스. 화면 12개 전부를 맡았습니다.

React · Vite · TypeScript · TanStack Query · MSW
108커밋 — 1위 (2위 59)
12담당 화면 W-01~W-12
3일테스트 0 → 전 화면 커버
문제

프론트에 테스트가 0개였고 CI가 프론트를 검사하지 않았습니다. 기능은 계속 늘어나는데 안전망이 없었고, 특히 위험한 건 눈으로 확인할 수 없는 것들이었습니다 — 보관함에서 삭제한 뒤의 상태, 뒤로가기 경로, 서버가 거절했을 때의 문구, 잔액을 알 수 없는 상황.

판단

순서를 이렇게 잡았습니다. Vitest 도입 → 프론트 검사 워크플로 신설 → 목 상태 격리부터. 테스트끼리 오염되면 나머지가 전부 무의미해지기 때문에 격리가 먼저였습니다.

그다음 되돌릴 수 없는 동작(삭제·뒤로가기·서버 거절·미상 잔액) → 대기·결과·계산기 → 로그인·OAuth 복귀 순으로 덮었습니다.

결과

사흘 만에 12화면 전체에 회귀 방지선이 생겼습니다. 이후 백엔드 계약이 바뀌어도 깨지는 지점이 CI에서 먼저 드러납니다.

접근성

요구받지 않은 작업입니다. 한 번에 훑어서 정리했습니다.

  • 모달 포커스 트랩·초기 포커스·복원 — 키보드 사용자가 모달 뒤로 빠져나가고 있었습니다
  • 로그인 시트가 떠 있는데 뒤 화면이 눌리던 것 — 시각적으로만 모달이었습니다
  • 버튼·탭 키보드 포커스 링 — 키보드로는 지금 어디 있는지 알 수 없었습니다
  • prefers-reduced-motion 대응 · 로딩 스켈레톤으로 레이아웃 점프 제거
  • 앱바 ← 버튼 터치 타겟 확대 · 12개 화면이 전부 같던 브라우저 탭 제목 수정
잡은 것

CDN을 붙이는 순간 이미지 저장이 저장이 아니게 되던 것(blob 우회로 해결), 문서에 없는 error_code 하나에 결과 화면이 통째로 죽던 것(미상 코드 폴백), 사진을 바꿔 골라도 남아 있던 이전 업로드 거절 문구, 갱신만 막힌 회원에게 원인도 해제 시점도 안 알리던 것.

재직 · 프론트 단독

SNS 댓글봇

SNS에서 키워드를 감시하고 사람이 승인 버튼을 눌러야만 답변이 나가는 웹앱입니다. 자동 게시 봇이 아닙니다.

React · TypeScript · Tailwind · MSW · 2026.07.20 – 08.12
51커밋 — 1위 (2위 42)
3주화면 전체 구축
범위

대시보드(매칭 리스트·필터·소스 헬스 배지), 매칭 상세·승인, 소스/키워드/템플릿/계정 CRUD, admin 사용자 관리, 감사 로그, Threads OAuth 연동까지 3주 안에 전부 올렸습니다.

문제

여러 건을 한 번에 승인·발송하는 기능을 붙이는데, 구조상 N건에 동일한 문구가 그대로 실려 나가게 되어 있었습니다. 기술적으로는 정상 동작이지만 플랫폼 입장에서는 스팸이고, 계정이 정지될 수 있습니다.

판단

백엔드 계약을 기다리지 않고 건별 문구 렌더로 전환했고, 발송 전 화면에서 각 건의 실제 문구를 확인할 수 있게 했습니다.

프론트엔드가 “화면만 그리는 자리”였다면 나오지 않았을 판단입니다. 이 화면이 실제로 어떤 결과를 만드는지를 보고 잡았습니다.
또

실패를 사람이 읽을 수 있게 만들었습니다. 소스 degraded/down 배지에 “왜”를 붙이고(상태만 빨간색이면 대응이 안 됩니다), 409 차단 사유를 “중복 답글”·“계정 삭제됨” 같은 문장으로 바꾸고, RSS 원문 HTML이 그대로 노출되던 것을 평문 정규화했습니다.

정합성 쪽으로는 CSRF가 아닌 403에도 뮤테이션을 재전송하던 것을 막고 단일비행(single-flight) 회귀 테스트로 고정했습니다. 그 외 앱 전체 모바일 반응형, 파비콘·로고 SVG 제작, 프론트 영역 규칙 문서를 디렉터리에 부착.

Lead-Crawler

기업 IR 연락처를 24/7 자동 수집하고 직원은 검증만 하는 시스템. 제가 만든 검증 웹앱이 그 “사람 1~2명”이 하루 종일 보는 유일한 화면이었습니다.

전제

이 화면의 처리 속도가 곧 필요한 인원 수입니다. 그래서 작업을 두 갈래로 나눴습니다.

처리량을
올리는 쪽
  • 큐 클레임 영구 배정 — 반납을 없애고 조회/받기를 분리해, 같은 건을 두 사람이 붙잡는 상황과 받아놓고 방치되는 건을 동시에 없앴습니다
  • 확정/거부 2단계 통일 — 마우스 클릭에도 확인 모달. 되돌리기 비용이 큰 동작입니다
  • 거부 Delete 단축키 — 하루 수백 건을 처리하는 화면에서 손이 마우스를 떠나지 않게
  • 확정/거부 번복 흐름의 dead end 해소 — 번복하려 하면 모달에서 길이 끊겨 있었습니다
  • 국가·업종·상장·시장·지역 다중 필터, 컬럼 정렬, 새로고침 시 탭 유지
처리량을
측정하는 쪽

이쪽이 더 중요합니다 — 일별·직원별 확정/거부 집계, 직원별 일일 검수 처리량 조회, 엑셀 추출의 확정 처리일(KST) 범위 필터.

인건비 절감은 시스템 전체의 성과입니다. 다만 “검증 1~2인 체제로 간다”는 계획이 실제로 도는지를 숫자로 확인할 수 있게 만든 자리는 제가 맡았습니다.
방법

npm run dev:mock — MSW 목 모드를 만들어 백엔드 없이 화면을 완성했습니다. 목 큐 100건을 넣어 대량 데이터에서의 레이아웃·성능까지 미리 확인했고, 백엔드 PR이 착지하면 그 PR 번호를 참조해 계약을 맞췄습니다.
